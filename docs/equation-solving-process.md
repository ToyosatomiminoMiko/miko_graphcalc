# 方程求解过程的展示设计

> **2026-09 状态说明:本文的"右栏标签页"前提已被窗口化推翻.**
> [面板窗口化设计计划](windowing-plan.md)(W6)把右栏那两个标签页("参数 /
> 视图"与"过程")以及"参数区 / 视图区"共用一层高度的分隔条一起拆掉,变成
> **五个独立窗口**:`source code` / `参数` / `视图` / `过程` / `对象`.
> 所以本文里"把过程做成右栏第二页""参数区与视图区共用高度"的结论按历史设计
> 读:过程现在是一个**独立窗口**(可单独拖宽,见 §2.2 的取舍),当年那条
> "右栏只有一份空间,一次只能看一页"的约束不再存在.其余内容(过程为什么要
> 板书画,步骤数据怎么来,分期口径)仍然有效.

一句话结论:**过程需要的不是"更大的盒子",而是"另一页".** 解方程/看推导的时候,
用户不会去拖参数滑块,也不会去切视图开关--这些"手不动的东西"就是可以被遮挡的.
所以不改浮层格局,不去抢三维视口,而是把**右栏改成标签页**:一页放现有的
"参数 / 视图",另一页通高地放过程.

分期口径:**一期只做展示层,零内核风险**;步骤产物,三维联动,符号求解内核
留到二/三期,边界见 [第 6 节](#6-分期与数据来源).

配套阅读:[教学化改造路线图](teaching-roadmap.md) 的 B1(步骤化求导)与 B5(本设计).

## 1 问题

### 1.1 空间实测

数字来自 `src/config/uiConfig.ts` 的 `UI_CONFIG.panel` 与 `css/layout.css`:

| 区域 | 现状 | 来源 |
| --- | --- | --- |
| 三维视口 | `position:absolute; inset:0`,铺满全窗口,所有面板浮在它上面 | `css/layout.css` `#viewport` |
| 左栏(源码) | 宽 220–875px(默认 300),通高 | `#left-panel` |
| 右栏(参数/视图) | 宽 220–875px(默认 300),**通高** | `#right-panel` |
| 底栏(对象清单) | 高 **160–640px**(默认 240),折叠后 40,夹在左右栏之间 | `#bottom-panel` |
| 底栏内部 | `1fr 1fr` 两栏(实体 \| 求值),各自纵向滚动 | `#object-panel` |
| 过程现状 | 求值条目里一个 `<details>`,展开后一行一条 KaTeX | `evaluationDom.ts` / `.eval-detail-body` |

底栏可用高度:`640 − 标题栏(约 33) − 面板内边距(16) − 栏标题(约 31) − 列表内边距(12)`
≈ **548px**.公式单行高度:KaTeX 字号 1.5em(24px)继承 body 行距,简单递等式
一行约 34px,加上 `.eval-detail-body` 的 3px 间隙约 **37px**;一旦出现分式/根号,
一行可达 **55–70px**.于是:

- 全是简单行:**约 14 行**见底;
- 含分式:**约 8 行**见底.

宽度同理:默认 1920px 屏,中间区 `1920 − 300 − 300 = 1320px`,底栏两栏各
**约 646px**;`sin`/`ln` 复合函数的链式展开很容易超出这个宽度,只能靠
`.eval-detail-line` 的横向滚动承接.

同一块屏,右栏通高可用的高度是 `100vh − 标题栏与内边距`,1080p 下约
**1020px ≈ 27 行简单式**--是底栏上限的两倍,而且**不与实体清单抢列宽**.

### 1.2 "把 footer 拖高"解决不了

1. **高度写死**:`footerMaxHeight: 640`,2K/4K 屏也还是 640,垂直空间白白浪费.
2. **宽度对半**:`#object-panel` 是 `1fr 1fr`,过程只能占一半,长等式必然横滚.
3. **共用容器**:过程与实体清单挤在同一个滚动区,展开一条就把别的条目挤出视野;
   而且行重建(`KeyedRowList` 的整行替换)会带来滚动位置跳动.
4. **没有"步"这个概念**(真正的缺口,见 1.3).

前三条是空间问题,第四条是设计问题.只解决前三条,得到的是一面更长的文本墙.

### 1.3 真正的缺口是交互模型

现在"看过程"只有一档:一次性把细节全展开.教学要的却是:

- **当前走到第几步**,而不是整段一次性给出;
- **这一步的依据**(链式法则 / 因式分解 / 同底数幂合并),而不只是等号两边;
- **几何跟着变**(拖动 `h->0` 时割线变切线,分割加细时黎曼矩形变密).

最后一条是本项目区别于"能解方程的 CAS"的地方,也是这条路线上唯一值得
不计成本做的部分.

## 2 设计原则

| # | 原则 | 含义 |
| --- | --- | --- |
| P1 | **遮挡"手不动的东西"** | 读推导时不会调参/调视图,所以右栏现有的那一页此时没有信息增量,让位给过程.不新增浮层,不压缩三维视口 |
| P2 | **保守式新增** | 一期只碰展示层:不改 Rust,不改 `contract/ir.ts` 既有字段语义,不新增 DSL 语句.求解内核是"不可避免但必须分期"的事,不许一步到位 |
| P3 | **三级披露** | 短过程留在原地(零改动),长过程才进过程页.判据是纯函数,阈值进配置 |
| P4 | **文案与数据分离** | 步骤的依据文案(如"链式法则")是数学内容,放纯数据模块,不硬编码进渲染逻辑(与 `src/config/uiConfig.ts` 的"只放纯数据"同一约定) |
| P5 | **可单测** | 披露判据,步骤分区都是纯函数/纯状态转移;碰不到 DOM 的部分必须能在测试里断言(路线图改造原则 4) |

## 3 版面:右栏标签页

### 3.1 目标结构

```text
<aside id="right-panel" class="panel">
  <header class="panel-header">          ← 折叠时唯一保留的一层
     <div id="right-tabs" role="tablist">  ← 新增:两个标签
        [参数 / 视图]  [过程]
     </div>
     <button data-panel-toggle="#right-panel">收起</button>
  </header>

  <div id="right-page-params" role="tabpanel" data-tab="params">   ← 新增:页1
     <section id="params-panel"></section>       (现有)
     <section id="diagnostics"></section>        (现有)
     <div id="right-splitter" data-split-page="right-page-params"></div>  (现有;数据属性为本次新增)
     <header class="panel-header">视图</header>  (现有)
     <section id="view-controls"></section>      (现有)
  </div>

  <div id="right-page-process" role="tabpanel" data-tab="process">  ← 新增:页2
     <section id="process-panel"></section>
  </div>

  <div class="resize-handle resize-handle-left" data-resize-panel="right-panel"></div>
</aside>
```

页容器**不写 `hidden` 初值**:默认哪一页在前只在 `RightPanelTabs` 的
`DEFAULT_RIGHT_TAB` 声明一处,构造期由 `_applyPages()` 写出页级显隐;HTML 里
再写一份初态就成了"改一处漏一处"的第二份副本.

要点:**两页的内容各自包一层**.原因见 3.2 的第 1 条--`PanelController` 的折叠
实现是"隐藏除承载开合按钮的那个 header 以外的全部直接子元素",包一层之后
页级显隐与折叠级显隐互不干扰,各自只有一个写入点.

标签页用 `role="tablist"` / `role="tab"` / `role="tabpanel"`,**不复用**
`ui/widgets/Segmented.ts`:后者的语义是"切换按钮"(`role="group"` +
`aria-pressed`,每个按钮都能 Tab 到),而标签页的键盘约定是"整组一个 Tab
停靠点 + 方向键在组内移动 + `aria-selected` + `aria-controls`,需要 roving
tabindex".语义不同强行复用会把读屏与键盘行为做成四不像.新写一个
`src/ui/widgets/Tabs.ts`,样式仍归 CSS,句柄契约(`element` / `get` /
`onChange` / `dispose`)与其他控件保持一致.

### 3.2 必须处理的四个耦合点

这一节是本次改动**唯一有真实风险**的地方,四处都在现有控制器里,漏一处就是
上一轮 UI 审查里那类"模型一套,DOM 一套"的缺陷(UI-P3.3).

1. **折叠语义**.`PanelController._applyLayout()` 会遍历面板的直接子元素,把
   非 header 的全部设成 `display:none`.标签页栏必须**放进那个 header 内部**,
   否则一折叠就再也切不回来;两页各自包一层 `<div>`,折叠时整页一起隐藏,
   不必给折叠逻辑加"哪些子元素算内容"的清单.

2. **分隔条的比例基准**.`RightSplitController.computeSplitRatio()` 现在拿
   `#right-panel` 的矩形当基准(理由是"参数区是右面板第一个子元素,顶边重合").
   加了标签页栏之后这条前提失效:参数区的顶边比面板顶边低了一个标签栏.
   改法是**把基准换成页容器**(`#right-page-params`),并在页容器上恢复
   `display:flex; flex-direction:column; flex:1; min-height:0`
   (`#params-panel { flex: 0 0 var(--right-split-basis) }` 的参照系随之从
   "右栏高度"变成"页高度",语义更准确).同时过程页激活时,`#right-splitter`
   与 `#params-panel` 整组退出布局,不能让 `flex-basis` 参与计算.

   跟进(实现后):这条"基准换成页容器"的连接不再由控制器按 id 找元素,而是
   分隔条自己带 `data-split-page="right-page-params"`.与 `PanelController` 的
   `[data-resize-panel]` 统一到同一约定--**数据属性负责连接,id 只留给锚点与
   无障碍**;`id="right-splitter"` 保留(样式,无障碍与 `RightSplitController`
   的样式契约测试仍按它定位),但删掉它不再影响控制器能否绑上.

3. **宽度的唯一写入点**.`--right-panel-width` 只有 `PanelController._applyLayout`
   一个写入点,这条不变量不能破(UI-P3.3 的教训).因此**过程页需要更宽的栏宽**
   这件事不能由标签页控制器直接写 CSS 变量,只能走 `PanelController`:

   - 曾建议按"**宽度组**"记宽(参数页 `params` / 过程页 `process`,切页 = 切宽度).
     实作后确认这是 bug 观感:切一次页栏宽就在 300 与 420 之间跳,用户看到的是
     "侧栏宽度不一致".
   - **最终采用单一份宽度**:左右各一份,右栏两个标签页共用;切页不改宽度,
     拖宽后两页同时生效.宽度仍然只有 `_applyLayout` 一个写入点.
   - 代价:过程页不再自动变宽,首屏沿用面板默认 300px(见 3.3),需要时手动拖.
   - 降级:标签栏上加"板书模式",一键把右栏推到上限(二期评估).

4. **行末按钮的契约**.过程入口按钮要挂在求值条目行末,但
   `createObjectRow(rowClass, toggle)` 只容得下**一个**按钮(显隐按钮),而且
   显隐按钮刻意不在 `<summary>` 里(点了不会开合).加第二个按钮必须把该函数
   的参数从"一个元素"改成"一个行末动作容器",并同步 `EntityItem` /
   `EvaluationItem` 两侧调用点与 `ObjectListController.test.ts` 的手写 DOM 桩.
   这是本次唯一要动的共享件,改完必须是一次纯签名扩展,不改变显隐按钮的
   位置语义(仍在行末,仍不在 `<summary>` 内).

### 3.3 宽度策略

右栏默认 300px 对递等式偏窄:一条 `sin(a·x)` 的链式展开即使不带分式也要
400–500px.落地方案:

- 参数页与过程页**共用一份宽度**,默认取面板默认值 **300px**,夹取范围沿用
  现有的 220–875;拖宽后切页不再跳变(见 3.2 第 3 条的最终结论);
- 若首屏仍嫌窄,可整体调大 `UI_CONFIG.panel.sideDefaultWidth`(注意它会同时
  加宽左源码栏),或做二期的"板书模式";
- 标签栏上加"板书模式":一键把右栏推到上限并折叠左栏与底栏.它需要
  `PanelController` 暴露一个"按 id 折叠/设宽"的编程入口--**一期不做**,先
  手动拖;二期再评估(它会让折叠态多一个写入路径,必须与 `_applyLayout`
  合并成同一处).

### 3.4 退化

- 视口宽 < 900px(或右栏拖到上限仍不足):过程页退化为**覆盖三维视口的整页**
  (`#right-panel` 临时 `left:0`),这是同一份内容换一套几何,不是第二套实现;
- 视口高 < 600px:过程页保留滚动,不改结构;
- 折叠态:沿用现有折叠,标签栏与标题一起隐藏,只剩"展开"按钮.

## 4 内容:过程视图

### 4.1 一行一步的递等式

每一行是"**左边关系符 + 一行 KaTeX + 右边依据徽章**",垂直排列,序号在左:

```text
 1   x^2 - 5x + 6 = 0                       原式
 2   (x - 2)(x - 3) = 0                     因式分解
 3   x - 2 = 0  或  x - 3 = 0               零积律
 4   x = 2  或  x = 3                       移项
```

实现上沿用现有约定:一行一个 LaTeX 字符串,交给 `FormulaView` 排版,
**公式不换行**,排不下时由该行横向滚动(KaTeX 换行会破坏公式语义,这是
`evaluationLatex.ts` 已经写明的取舍).与现有细节行的区别只有两点:多了序号与
依据两列,以及当前步高亮.

### 4.2 步骤分类:求导法则 vs 代数化简

路线图 B1 的风险①明确要求:**化简规则与求导法则不是一个概念**,混在一起学生
会把"同底数幂合并"当成求导.因此每一步带一个 `kind`:

| kind | 展示 | 例子 |
| --- | --- | --- |
| `rule` | 强调色徽章 | 链式法则,积法则,商法则,幂法则 |
| `algebra` | 中性色徽章 | 因式分解,通分,移项,同底数幂合并 |
| `definition` | 虚线徽章 | 导数定义式,导数定义代入 |
| `numeric` | 等宽数字 | 数值代入,差商校验(路线图 T8) |

一期没有内核产物时,`kind` 由数据源标注;三期由 Rust 步骤产物给出,UI 不变.

### 4.3 求解内核的板书口径(三期 v1)

系数是参数(`param a = 1; solve S = a*x^2 - 2 = 0;`)时,过程里有两条硬约定:

1. **系数取值单独成一步**,紧跟"原式":方程与各参数当前值叠成两行
   (`\begin{gathered} a x^{2} - 2=0 \\ a=1 \end{gathered}`).列的是**方程里
   真正用到的参数**(按出现先后),声明了但没用到的参数不列;方程里没有参数
   就没有这一步,不给空壳.方程本身**保留符号写法**,不把 `a` 直接换成 `1`--
   读者要能同时看到"哪个系数"和"它现在是多少";拖动滑块时,这一步就是唯一
   能看出"代进去的数变了"的地方.
2. **公式模板一律代入**:判别式与求根公式里的 `a`/`b`/`c` 都换成数值,
   不在换元之后停在 `-b` / `2a` 这样的字母上.判别式是完全平方时给精确根号
   (`\sqrt{8}`),否则给 `\sqrt{\Delta}`;`\Delta = 0` 时不给装饰性的
   `\pm \sqrt{0}`(重根只有一个值).

为什么用步内换行而不是继续接在一行后面:参数多起来或方程本身很长时,一行放
不下会横向滚动,而系数恰好是最不该被滚出屏幕的部分.步内换行是 LaTeX 自己
的排版(`gathered`),不动过程页"一行一步"的结构与行缓存.

例子(`a*x^2 - 2 = 0`,a=1):

```text
1   a x² − 2 = 0                                          原式
    a=1
2   Δ = 0² − 4 · 1 · (−2) = 8                             判别式
3   x = (+0 ± √8) / 2                                     求根公式
4   x₁ ≈ −1.414213562373095, x₂ ≈ 1.414213562373095       数值近似
```

### 4.4 当前步与交互(v1 后为**只读列表**,无游标)

一期曾实现"当前步高亮一行,其余降饱和度 + `上一个 / 下一个` 按钮 + 键盘左右
方向键 + 点击任意行跳转",并配一个纯状态机 `processState.ts` 与 `onStepChange`
出口.实测后**整体移除**,三条原因:

- **不隐藏任何东西**:后续步骤照样全部渲染,`is-current` 的全部效果只是
  `opacity 0.72 -> 1` 加一条 2px 强调色左边框,读不出"讲到哪";
- **不驱动任何东西**:`onStepChange` 本是二期"第 k 步当虚拟参数驱动几何"的
  接口,但生产代码里零消费者--一期唯一的可观测效果就是那个高亮;
- **本节原文承诺的滚动也没实现**:"高亮与滚动是面板自己的 DOM 写入"里没有
  `scrollIntoView`,过程超过一屏后按"下一个"连视觉变化都没有.

现在:**整条过程一次铺开,行是只读的**(见 `src/ui/process/ProcessPanel.ts`
头注释).同期删除的还有 `processState.ts` 及其单测,`css/process.css` 的
`.process-nav` / `.process-counter` / `.process-step.is-current`,以及 `DslApp`
注册进 `KeyboardController` 的左右方向键绑定.

**若要重做**:二期的"步骤索引驱动几何"应当和那时真正的交互一起设计(要披露就
真的披露,要联动就真的联动),不复用已删除的 `onStepChange` 残接口.

### 4.5 空状态与上限

- 没有可展示的过程时给一句明文("该对象没有可展开的过程"),不要给空盒子.
- 步骤上限:超长过程必须**截断并注明**,不能无上限铺开.上限值进
  `uiConfig.ts`(纯数据),与 `FormulaView` 的模板缓存上限(512)分开算:
  步骤行的 LaTeX 键是"表达式签名 × 步数",是有限集合,不需要扩容,但需要
  上限本身有明确语义.
- 隐藏对象(`enabled === false`)不参与计算,也就没有数值可展示:过程入口
  置灰并给理由,与"已隐藏,不参与计算"的现有文案口径一致.

## 5 三级披露与阈值

| 级别 | 位置 | 长度预算 | 状态 |
| --- | --- | --- | --- |
| L0 摘要行 | 条目第一行 | 1 行 | 已有,不动 |
| L1 行内展开 | 条目 `<details>` | ≤ N 行 | 已有,保留给短过程 |
| L2 过程页 | 右栏"过程"标签页 | 通高 | 新增 |

判据是一个纯函数:

```ts
// 细节行数超过阈值就走 L2;阈值进 UI_CONFIG,不进代码字面量
export function needsProcessPage(lines: readonly EvaluationDetailLine[]): boolean
```

- 短过程(梯度:符号展开 + 数值 + 球坐标回显,通常 3–5 行)继续留在
  `<details>`,用户不必切页,老路径一行不改;
- 长过程(逐步求导,求解,分割加细)在条目上出现"过程"按钮,点击后
  **右栏切到过程页并载入该条目**;

## 11 联立方程组(v1):统一求解词汇的落地

### 11.1 为什么长在 `solve` 上

联立与单方程服务的是同一件事--解约束,只是方程数 / 未知量数 / 方法不同.
因此 v1 **不新开语句**,而是扩展 `solve`:

```text
solve S = x^2 - 5*x + 6 = 0 { variable = x; };              // 单方程(原有)
solve S = { x + y = 3; x - y = 1; };                        // 联立(新增)
solve S = { x^2 + y^2 = 1; x - y = 0; } { range = [-2, 2]; segments = 24; };
solve S = { x^2 + y^2 = 1; x - y = 0; } { method = exact; }; // 只走精确后端
```

理由:显隐集合,名查重,求值列表子项,过程页骨架,参数系数链路在 `solve` 上
已经齐备;新开语句等于把这些各抄第七份(见 `contract/ir.ts` 的
`ConstraintTaskBase` 与 `compiler/dsl/statementShell.ts`).

### 11.2 统一词汇

| 层 | 单方程 | 联立 |
| --- | --- | --- |
| 内核问题 | `ConstraintKind::Equation` | `ConstraintKind::System` |
| 内核方法 | `exact` | `method` 选项:`auto`(缺省,线性精确 / 非线性数值)/ `exact` / `numeric` |
| 结果 | `ConstraintOutcome`(统一) | 同左 |
| IR 方程 | `equations = [原方程]` | `equations = [方程1, 方程2, ...]` |
| IR 未知量 | `unknowns = [x]` | `unknowns = [x, y]` |
| 题目 | `equationLatex`(原方程) | `equationLatex`(`cases` 方程组) |

IR 里只有 `equations` 与 `unknowns` 两个结构化字段:摘要的纯文本回退
(`equations.join('; ')`)与细节的"求解 X"(`unknowns.join(', ')`)都由 UI 派生,
不再并存"首条方程"与"连接串"这类同名不同义的派生字段.

`method` 记的是**内核实际用的后端**:请求 `auto` 时,线性方程组回报 `exact`,
非线性回报 `numeric`;能力边界回报"实际尝试过的那条路".单方程没有数值后端,
`method = numeric` 在编译期就报错.

### 11.3 能力边界(刻意保守)

| 情形 | 处理 |
| --- | --- |
| 线性,方程数 = 未知量数,系数矩阵可逆 | 精确解:原式 -> 标准形 -> 加减消元 -> 回代 |
| 非线性 | 数值路径:网格起点 + 阻尼 Newton;过程里标明搜索区间与"数值解" |
| 方程数 > 未知量数(超定) | 能力边界:"方程数多于未知量数" |
| 未知量数 > 方程数(欠定) | 能力边界:"解不唯一,暂不给通解" |
| 系数矩阵奇异 | 能力边界:"无解或有无穷多解" |
| 指定 `method = exact` 但方程非线性 | 能力边界,并提示精确路径只解线性方程组 |
| 区间内找不到数值解 | 能力边界,提示调整 `range`/`segments` |
| 网格节点数 `(segments+1)^未知量` 超过上限 | 能力边界,提示减小 `segments`(见 11.4) |
| 系数不是有限实数(如参数取负后开平方) | 能力边界,理由说明是哪一项;绝不把 `NaN`/`inf` 当解排版 |

**不伪造消元推导**:非线性方程组的中间步骤与线性消元不是一回事,所以数值路径
只给"数值解"这一步,并明确写出搜索区间与"不保证不漏根".

### 11.4 数值底座

数值路径复用 crate 级 `numeric_core`(202609 统一整理时从 `intersection_core` 与 `symbolic` 提到 crate 级):

- `numeric_core::roots`:一维符号扫描 + 点/根去重(求交与联立共用);
- `numeric_core::linalg`:高斯消元(部分分式与线性联立共用);
- `numeric_core::newton`:方阵系统阻尼 Newton + 盒域多起点扫描(联立数值路径).

规模守卫在**求值之前**判:`newton::grid_node_count` 给出节点数 `(segments + 1)^未知量`,
`symbolic::system` 拿它与上限(`MAX_NUMERIC_STARTS × 16 = 65536`)比较,超限直接给
能力边界.为什么必须先判:网格节点是逐个求值的(每个节点还要为 Jacobian 再求若干次),
只在选起点时截断等于先付了全部求值代价--实测 3 未知量 / `segments = 64`(274,625 个
节点)单次编译约 190ms,峰值内存约 26MB,而联立求解跑在主线程上,参数滑块每动一次
就重算一遍.

起点选择(`newton::select_starts`)先按初始残差升序,再按盒域分格去偏(每格最多一个
起点).只做前者的话,一个"残差平坦"的盆地会挤满小残差节点,吃光全部起点配额,
另一个盆地的解连起点都轮不到.

### 11.5 明确不做(v1)

- 不做符号系数代数:参数仍按当前滑块值代入(与积分 / 分析 / 单方程一致);
- 不给欠定方程组的通解参数化;
- 不做数值解的几何下发(解点是 `x, y` 变量空间,不是三维世界坐标);
- 不做高维(> 3 未知量)数值求解.

`range` 支持两种写法:一条区间广播到全部未知量(`range = [-2, 2]`),或逐个未知量
一条(`range = [-2, 2, -3, 3]`,条数必须与未知量数相等);条数不对由内核给理由.
